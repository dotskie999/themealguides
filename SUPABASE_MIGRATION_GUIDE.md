# Google Sheets to Supabase migration guide

This guide is written for the current The Meal Guides application and its existing Google Sheets database.

The first migration should preserve the current data shape. Do not redesign the app and database simultaneously. After the Supabase version is working, orders can be normalized into separate order-item tables and the spreadsheet PIN can be replaced with Supabase Auth.

## Current spreadsheet tabs

Migrate these tabs:

1. `Restaurants`
2. `Categories`
3. `MenuItems`
4. `OptionGroups`
5. `Options`
6. `Orders`

Do not import these tabs:

- `AdminAuth`: replace this with a server-side environment variable temporarily, then Supabase Auth.
- `Order_Counter`: Supabase/Postgres will generate order numbers.
- `Ingredients` and `ItemIngredients`: leave these in Sheets until the app implements inventory features.

Keep the Google Sheet unchanged as a rollback copy until the Supabase application has been verified.

## 1. Create the Supabase project

1. Create a project at <https://supabase.com/dashboard>.
2. Choose a strong database password and save it in a password manager.
3. Open **Project Settings > API**.
4. Record the project URL and create or copy a server secret key.
5. Never place the secret key in browser code or in a variable beginning with `NEXT_PUBLIC_`.

Use the current publishable/secret key system when available. The secret key is only for trusted server code.

## 2. Create the database schema

Open **SQL Editor** in Supabase, create a new query, paste the following SQL, and run it once.

```sql
create table public.restaurants (
  restaurant_id text primary key,
  name text not null,
  logo_url text,
  description text,
  active text not null default 'yes' check (active in ('yes', 'no')),
  banner_url text,
  address text,
  latitude double precision check (latitude is null or latitude between -90 and 90),
  longitude double precision check (longitude is null or longitude between -180 and 180),
  delivery_radius_km numeric(6, 2) not null default 10 check (delivery_radius_km > 0)
);

create table public.categories (
  category_id text primary key,
  restaurant_id text not null references public.restaurants(restaurant_id) on delete restrict,
  name text not null,
  active text not null default 'yes' check (active in ('yes', 'no')),
  sort_order integer not null default 0
);

create index categories_restaurant_idx
  on public.categories (restaurant_id, sort_order);

create table public.menu_items (
  item_id text primary key,
  restaurant_id text not null references public.restaurants(restaurant_id) on delete restrict,
  name text not null,
  base_price numeric(12, 2) not null default 0 check (base_price >= 0),
  category text,
  photo_url text,
  active text not null default 'yes' check (active in ('yes', 'no')),
  category_id text not null references public.categories(category_id) on delete restrict,
  description text
);

create index menu_items_restaurant_idx
  on public.menu_items (restaurant_id, category_id);

create table public.option_groups (
  group_id text primary key,
  item_id text references public.menu_items(item_id) on delete cascade,
  group_name text not null,
  selection_type text not null check (selection_type in ('single', 'multiple')),
  required text not null default 'no' check (required in ('yes', 'no')),
  sort_order integer not null default 0,
  category_id text references public.categories(category_id) on delete cascade,
  constraint option_groups_target_check check (
    nullif(btrim(item_id), '') is not null
    or nullif(btrim(category_id), '') is not null
  )
);

create index option_groups_item_idx
  on public.option_groups (item_id, sort_order);

create index option_groups_category_idx
  on public.option_groups (category_id, sort_order);

create table public.options (
  option_id text primary key,
  group_id text not null references public.option_groups(group_id) on delete cascade,
  option_name text not null,
  price numeric(12, 2) not null default 0 check (price >= 0),
  sort_order integer not null default 0
);

create index options_group_idx
  on public.options (group_id, sort_order);

create table public.orders (
  order_number bigint generated by default as identity primary key,
  restaurant_id text not null references public.restaurants(restaurant_id) on delete restrict,
  items_json jsonb not null,
  subtotal numeric(12, 2) not null check (subtotal >= 0),
  customer_name text not null,
  customer_email text,
  contact_number text not null,
  city text not null,
  barangay text not null,
  house_number text not null,
  landmark text,
  order_remarks text,
  delivery_latitude double precision,
  delivery_longitude double precision,
  distance_km numeric(8, 2),
  status text not null default 'pending'
    check (status in ('pending', 'confirmed', 'preparing', 'ready', 'completed', 'cancelled')),
  timestamp timestamptz not null default now()
);

create index orders_status_timestamp_idx
  on public.orders (status, timestamp desc);

create index orders_restaurant_timestamp_idx
  on public.orders (restaurant_id, timestamp desc);

create table public.guests (
  guest_id uuid primary key,
  customer_name text not null,
  customer_email text not null,
  contact_number text not null,
  city text not null,
  barangay text not null,
  house_number text not null,
  latitude double precision check (latitude is null or latitude between -90 and 90),
  longitude double precision check (longitude is null or longitude between -180 and 180),
  location_accuracy double precision,
  consent_at timestamptz not null,
  first_visited_at timestamptz not null default now(),
  last_visited_at timestamptz not null default now(),
  visit_count integer not null default 1 check (visit_count > 0)
);

create index guests_last_visited_idx
  on public.guests (last_visited_at desc);
```

The `active` and `required` fields intentionally remain `yes`/`no` text during the first migration. That matches the existing frontend and avoids unnecessary application changes during cutover.

## 3. Lock down the tables

The current app can perform every database operation through Next.js server code. The browser does not need direct table access.

Run this after creating the tables:

```sql
alter table public.restaurants enable row level security;
alter table public.categories enable row level security;
alter table public.menu_items enable row level security;
alter table public.option_groups enable row level security;
alter table public.options enable row level security;
alter table public.orders enable row level security;
alter table public.guests enable row level security;

revoke all on table public.restaurants from anon, authenticated;
revoke all on table public.categories from anon, authenticated;
revoke all on table public.menu_items from anon, authenticated;
revoke all on table public.option_groups from anon, authenticated;
revoke all on table public.options from anon, authenticated;
revoke all on table public.orders from anon, authenticated;
revoke all on table public.guests from anon, authenticated;

grant all on table public.restaurants to service_role;
grant all on table public.categories to service_role;
grant all on table public.menu_items to service_role;
grant all on table public.option_groups to service_role;
grant all on table public.options to service_role;
grant all on table public.orders to service_role;
grant all on table public.guests to service_role;
grant usage, select on all sequences in schema public to service_role;
```

With this configuration, no visitor can query or modify the tables directly using a publishable key. The Next.js server will be the trusted API layer.

## 4. Export the Google Sheets tabs

For each tab being migrated:

1. Open that tab in Google Sheets.
2. Select **File > Download > Comma-separated values (.csv)**.
3. Give the file the same name as the source tab, such as `Restaurants.csv`.
4. Do not change IDs such as `r_001`, `cat_001`, or `item_002`.
5. Ensure prices and sort orders contain numbers, not currency-formatted text.
6. In `Orders.csv`, ensure `items_json` still contains valid JSON.

Before importing, rename the CSV header fields only where the Supabase table name differs. The column names themselves already match the schema above.

## 5. Import the CSV files

In Supabase, open **Table Editor**, select the target table, and use **Insert > Import data from CSV**.

Import in this exact order so foreign keys can be validated:

1. `Restaurants.csv` into `restaurants`
2. `Categories.csv` into `categories`
3. `MenuItems.csv` into `menu_items`
4. `OptionGroups.csv` into `option_groups`
5. `Options.csv` into `options`
6. `Orders.csv` into `orders`

If an empty spreadsheet cell imports as an empty string where Supabase expects `NULL`, replace that cell with a true blank/null during the import preview.

An option group may contain both an `item_id` and a `category_id`, matching the existing spreadsheet and application behavior. At least one of those fields must be populated.

After importing orders, synchronize the Postgres order-number sequence:

```sql
select setval(
  pg_get_serial_sequence('public.orders', 'order_number'),
  greatest(coalesce((select max(order_number) from public.orders), 1000), 1000),
  true
);
```

The next order will then receive the next unused number.

## 6. Verify the imported data

Run these checks in SQL Editor:

```sql
select 'restaurants' as table_name, count(*) from public.restaurants
union all select 'categories', count(*) from public.categories
union all select 'menu_items', count(*) from public.menu_items
union all select 'option_groups', count(*) from public.option_groups
union all select 'options', count(*) from public.options
union all select 'orders', count(*) from public.orders;

select c.category_id
from public.categories c
left join public.restaurants r on r.restaurant_id = c.restaurant_id
where r.restaurant_id is null;

select m.item_id
from public.menu_items m
left join public.categories c on c.category_id = m.category_id
where c.category_id is null;

select o.option_id
from public.options o
left join public.option_groups g on g.group_id = o.group_id
where g.group_id is null;

select order_number
from public.orders
where jsonb_typeof(items_json) <> 'array';
```

Each orphan query and the invalid JSON query should return zero rows. Compare every table count with the corresponding Google Sheets tab.

## 7. Connect the local Next.js app

Install the JavaScript client from the project directory:

```powershell
npm.cmd install @supabase/supabase-js
```

Add these values to `.env.local`:

```env
SUPABASE_URL="https://YOUR_PROJECT_REF.supabase.co"
SUPABASE_SECRET_KEY="sb_secret_YOUR_SERVER_SECRET"
```

Do not use `NEXT_PUBLIC_SUPABASE_SECRET_KEY`. A variable prefixed with `NEXT_PUBLIC_` can be included in browser JavaScript.

Create a server-only client, for example `src/lib/supabaseAdmin.js`:

```js
import 'server-only';
import { createClient } from '@supabase/supabase-js';

if (!process.env.SUPABASE_URL || !process.env.SUPABASE_SECRET_KEY) {
  throw new Error('Supabase server configuration is missing.');
}

export const supabaseAdmin = createClient(
  process.env.SUPABASE_URL,
  process.env.SUPABASE_SECRET_KEY,
  {
    auth: {
      persistSession: false,
      autoRefreshToken: false,
      detectSessionInUrl: false,
    },
  },
);
```

Then replace the implementation in `src/lib/api.js` while keeping its existing exported functions:

- `getRestaurants()` reads active rows from `restaurants`.
- `getMenu(restaurantId)` reads menu items, option groups, and options and returns the same nested shape used by `MenuClient`.
- `submitOrder(payload)` inserts into `orders` and returns the generated order number.
- Admin save actions use `.upsert()` with the corresponding primary key.
- Order status updates use `.update()` and still prevent completed orders from changing.

Keeping the existing function interface means most React components will not need to change.

## 8. Test before cutting over

Test all of these locally:

1. Homepage lists active restaurants.
2. Every restaurant route loads its categories, menu items, groups, and options.
3. A test order receives the next order number.
4. The receipt page displays the submitted order.
5. Admin login rejects invalid credentials.
6. Admin can create and edit restaurants, categories, items, groups, and options.
7. Admin can advance an order through each status.
8. A completed order cannot be changed.
9. A browser cannot query Supabase tables directly with a publishable key.

Only after these pass should `NEXT_PUBLIC_API_URL` and the Google Apps Script dependency be removed from the application.

## 9. Replace the spreadsheet PIN

For the initial database cutover, move the admin PIN from `AdminAuth!A2` into a server-only environment variable. Do not store it in Supabase as plain text.

The recommended follow-up is to replace the PIN with Supabase Auth:

1. Create one admin user in Supabase Auth.
2. Create an `admin_users` or `profiles` table linked to `auth.users.id`.
3. Store an administrator role in that table.
4. Use cookie-based server-side sessions in Next.js.
5. Verify the authenticated user and administrator role before every admin mutation.

## Recommended cutover sequence

1. Keep Google Sheets live while building the Supabase adapter.
2. Import a fresh copy of the data into Supabase.
3. Test the app against Supabase locally.
4. Temporarily stop accepting orders through the Sheet-backed version.
5. Import any orders created since the first test import.
6. Switch `.env.local` and the data adapter to Supabase.
7. Submit one controlled test order.
8. Keep the spreadsheet read-only as a backup until the new database is stable.

Do not write orders to both systems during normal operation. Dual writes can leave the two databases inconsistent when one request succeeds and the other fails.
